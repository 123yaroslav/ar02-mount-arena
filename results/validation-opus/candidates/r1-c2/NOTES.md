# r1-c2. Режимы фонового потока по поведению агента и заранее взятые края большого файла

Родитель r1-c1. Направление исследователя это задержка пути чтения.

## Гипотеза

После r1-c1 чтение почти всегда идет из кэша. Остаток задержки чтения и записи на быстром канале создает сам фоновый поток. Ответ агенту ждет за сырой порцией фона по 128 КБ, это 20 мс на RTT 1 мс. Агент, который догнал фронт потока, ждет сырые байты, хотя словарь строк передал бы их в 10 раз быстрее. Первое чтение большого файла стоит полный круг. Если выбирать форму потока по тому, что сейчас делает агент, и заранее взять начало и конец большого файла, эти задержки уйдут без лишнего CPU.

## Что изменено

Режимы фона на быстром канале (от 3 МБ/с). Агент догнал фронт потока, то есть запрошенный файл лежит не дальше 128 позиций позади указателя потока или 64 впереди. Тогда фон идет короткими порциями через словарь строк. Агент просто читает (запрос чтения за последнюю секунду), тогда фон сырой порциями по 32 КБ. Агент только пишет, тогда фон стоит на паузе, пока запись не затихнет на секунду, и ответы на записи не ждут за ним. Агент молчит, тогда фон сырой порциями по 128 КБ, как в r1-c1.

Края больших файлов. На быстром канале сразу после замера полосы сервер шлет начало (128 КБ) и конец (64 КБ) трех самых больших файлов. Если агент читает большой файл из кэша, клиент один раз шлет серверу подсказку без ответа, и сервер начинает поток остатка. Поток остатка сжимается zlib 1, только пока агент запрашивает его блоки. Иначе он идет сырым, так дешевле по CPU.

Блок большого файла на канале медленнее 1 МБ/с равен 16 КБ вместо 64 КБ. Размер выбирает клиент по полосе и сообщает серверу вместе с полосой. Так одна порция бинарного файла на 88 КБ/с длится 0,18 с, а не 0,74 с, и пульс не застревает.

Проба сжимаемости zlib на 16 КБ больше не запускается на первом файле каждой сырой текстовой порции. Она нужна только большим файлам.

Ни один вид не стал хуже, на rtt=20 loss=0.01 x0.97, и прогон в одном процессе показал, что там это шум.

## Что узнал

Самый большой выигрыш дали края большого файла. На RTT 200 мс без потерь ожидание big_file упало с 0,25 с до нуля, на маленьких деревьях ускорение выросло в 4-9 раз.

Негативный результат 1. Заранее качать на быстром канале весь большой файл после текста. Это стоило 5-12 мс CPU в каждом сценарии, на маленьких деревьях файл в 4-9 МБ больше всего текста. В паре с вариантом без этого он проиграл x0.94 по сумме, хотя big_file выиграл. Остаток большого файла теперь идет только по подсказке.

Негативный результат 2. Включать словарь строк при любом чтении агента. Одно чтение в сценарии writes переводило весь остаток потока в словарь, около 13 МБ кодирования впустую, и writes на RTT 1 мс стал хуже r1-c1. Словарь окупается, только когда агент ждет сам поток, отсюда признак догнавшего фронт. Первая версия признака смотрела только вперед от указателя потока и не срабатывала, потому что запрошенные файлы уже были в пути, чуть позади указателя.

Негативный результат 3. Блок 16 КБ на медленном канале убрал синхронизации и ожидание stat в big_file (1,0 с на RTT 200 мс с потерями), но ожидание чтения выросло на столько же. Там предел задает передача бинарного файла, общее время не изменилось.

Сжатый поток большого файла на быстром канале нужен, только когда агент его ждет. Текстовый лог 4 МБ на 6,25 МБ/с идет 0,23 с через zlib 1 и 0,67 с сырым, а CPU на zlib тратится всегда.

Что осталось. Чтение близко к пределу полосы. Главный остаток это ожидание записей (writes x1.4, в session записи дают почти все ожидание на большом RTT) и постоянный CPU снимка папки и вызовов раннера на RTT 1 мс.
