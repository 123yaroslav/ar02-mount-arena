# Домен. Протокол монтирования workdir при разных задержках сети

## Постановка

LLM-агент для кода работает в удаленной песочнице. Локальная папка пользователя смонтирована туда как рабочая директория агента. Между ФС-вызовами агента и диском пользователя стоит протокол монтирования. Его код и эволюционирует на арене.

Вход это трасса файловых операций и параметры сети. Трассы покрывают типовые нагрузки агента.

- Обход дерева со `stat` на каждый файл.
- `grep` по всему дереву.
- Чтение многих мелких файлов.
- Последовательное чтение одного большого файла или только его начала и конца.
- Серия записей.
- Смешанная сессия, где между вызовами инструментов агент думает 2-8 с.
- Правки пользователя в редакторе параллельно с агентом.

Сеть задаем сеткой. RTT 1, 20, 80 и 200 мс, потери 0 и 1%, полоса около 50 Мбит/с.

Выход это код протокола. Он состоит из клиента в песочнице и сервера на машине пользователя. Кандидата прогоняем в детерминированном симуляторе сети с виртуальным временем и меряем время выполнения нагрузок.

Кандидат должен пройти пять гейтов консистентности. Если нарушен хотя бы один, скорость не засчитывается.

1. Запись агента видна на машине пользователя не позже чем через T = 1 с.
2. Правка пользователя видна агенту не позже чем через T.
3. После unmount не потеряна ни одна запись.
4. Режим только для чтения соблюдается.
5. Агент не выходит за пределы смонтированной папки.

Хорошее решение близко к локальному диску на всех RTT, проходит все гейты и не тратит полосу зря. Главная трудность в RTT 200 мс. Там каждый лишний круг до пользователя стоит 0,2 с. Обход дерева из 1000 файлов с отдельным `stat` на каждый займет около 200 с, если запросы идут строго по одному. Чтение файла на 10 МБ при 50 Мбит/с занимает около 1,6 с только на передачу. Оптимизировать нужно по двум осям, число кругов по сети и объем данных.

## Классические подходы

| Подход | Идея | Сильные стороны | Слабые стороны | Известные оценки |
|---|---|---|---|---|
| NFSv3 | Кэш атрибутов с TTL и close-to-open. При open клиент сверяет атрибуты с сервером, при close сбрасывает изменения. READDIRPLUS отдает имена вместе с атрибутами. | Простая модель. Кэш данных живет между open. Обход каталога за меньшее число кругов. | Чужие правки видны с задержкой до TTL. Опция `noac` убирает кэш и делает запись синхронной. | По умолчанию `acregmin=3`, `acregmax=60`, `acdirmin=30`, `acdirmax=60` секунд. `lookupcache=pos` перепроверяет отсутствующие имена. |
| NFSv4 делегации | Сервер выдает клиенту делегацию на файл и обещает callback, если файл откроет другой клиент. COMPOUND объединяет несколько операций в один запрос. | Пока делегация действует, клиент работает с файлом без проверок по сети. | Нужен обратный канал от сервера. Linux-клиент не поддерживает делегации на каталоги. | Чисел для нашего сценария не нашли, оценка качественная. |
| SSHFS поверх SFTP | Каждая операция ФС превращается в запрос SFTP и ждет ответа. Имена и атрибуты кэшируются с TTL. | На стороне пользователя нужен только sshd. Чтение по умолчанию асинхронное. | Каждый `stat` и `open` платит полный RTT. На большом RTT обход дерева и `grep` медленные. | sshfs 2.x `cache=yes` и `cache_timeout=20` с по умолчанию. FUSE `entry_timeout` и `attr_timeout` по 1 с, `negative_timeout` 0. `kernel_cache` не сбрасывает кэш содержимого при каждом open. |
| 9P | Протокол Plan 9 с отдельным запросом на walk, open, read и stat. WSL2 монтирует через него диски Windows (`/mnt/c`), gVisor использовал его между sandbox и gofer и ходил по пути отдельным RPC на каждый компонент. | Простой протокол. Есть в ядре Linux (v9fs) и транспорт через virtio. | Много мелких RPC. gVisor назвал свой вариант 9P «very chatty» и заменил на LISAFS. Microsoft пишет, что WSL2 медленнее WSL1 на файлах Windows. | В gVisor `stat(/foo/bar/baz)` в VFS1 стоил 3 RPC, в VFS2 с LISAFS один. LISAFS ускорил холодный старт App Engine больше чем на 25%. |
| virtiofs | FUSE поверх virtio между хостом и локальной ВМ. DAX отображает содержимое файла из page cache хоста прямо в память гостя. | Семантика близка к локальной ФС, сетевого стека нет. | Работает только для ВМ на том же хосте. Через сеть не применим. | Docker пишет, что VirtioFS сократил время файловых операций до 98%. |
| AFS | Клиент скачивает файл целиком в дисковый кэш. Сервер обещает callback, если файл изменится. | Повторные открытия обходятся без сети. Клиент не сверяет кэш с сервером на каждое open. | Первое открытие большого файла ждет весь файл. Чужие изменения видны после close. | Howard и др. (1988) сравнили Andrew с NFS и обосновали передачу и кэш целых файлов. Оценка для нас качественная. |
| Coda | Наследник AFS. Клиент заранее подтягивает нужные файлы (hoarding), без связи работает из кэша и пишет журнал, после восстановления связи проигрывает журнал на сервере. | Работа при обрыве связи. | Возможны конфликты правок, часть решает пользователь вручную. | Kistler и Satyanarayanan, TOCS 1992. Чисел для нашего сценария нет. |
| LBFS | Файл режется на чанки по содержимому (Rabin fingerprint по окну 48 байт). Передаются только чанки, которых нет у получателя. | Вставка в середину файла меняет один-два чанка, остальное не передается. Хорошо работает на правках и автосохранениях. | Нужны индексы чанков с обеих сторон и хэширование. Экономит полосу, но не круги. | Больше чем на порядок меньше трафика, чем у обычных сетевых ФС на типовых нагрузках. Ожидаемый размер чанка 8 КБ. |
| rclone mount | Режимы кэша VFS `off`, `minimal`, `writes`, `full`. Чтение кусками, кэш каталогов и атрибутов с TTL, отложенная выгрузка записей. | Режим подбирается под нагрузку. `full` кэширует на диске и чтение, и запись. | С кэшем каталогов чужие правки видны с опозданием. Запись в режимах с кэшем уходит с задержкой. | По умолчанию `--dir-cache-time` 5m, `--attr-timeout` 1s, `--vfs-write-back` 5s, `--vfs-read-chunk-size` 128M. |
| Mutagen и Docker Desktop | Двусторонняя синхронизация полной копии дерева. Изменения ловит watcher, передаются дельты в духе rsync. Docker на Mac прошел путь osxfs, gRPC FUSE, VirtioFS и добавил synchronized file shares на Mutagen. | Чтение у агента локальное и не зависит от RTT. | Нужна начальная копия всего дерева. Возможны конфликты. Видимость правок зависит от скорости цикла синхронизации. | Docker обещает файловые операции в 2-10 раз быстрее bind mount. Лимит около 2 млн файлов на share. VirtioFS по умолчанию для новых установок с 4.21, для всех с 4.23 (2023), synchronized file shares с 4.27 (январь 2024). |
| FUSE readahead и page cache | Ядро читает с опережением и держит страницы в page cache. Размер одного запроса к демону ограничен. | Большой файл читается крупными блоками, повторное чтение идет из памяти. | Writeback cache в libfuse по умолчанию выключен. Без `kernel_cache` кэш содержимого сбрасывается при open. | Запрос по умолчанию 32 страницы (128 КиБ), с Linux 4.20 до 256 страниц (1 МиБ) через `max_pages`. |
| VS Code Remote | Файлы не монтируют. Серверная часть ставится рядом с файлами и выполняет там поиск, анализ и расширения. | По сети ходят команды и результаты, а не содержимое файлов. | Нужен процесс на стороне файлов. Интерфейс уже не ФС. | Microsoft обещает работу на уровне локальной разработки, чисел не дает. |

Через все подходы проходят три выбора.

Запись. Write-through отправляет каждую запись сразу и ждет подтверждения. Это просто и безопасно, но каждая запись стоит RTT. Write-back копит изменения и сбрасывает пачкой, например при close в NFS или через 5 с после последнего использования в rclone. Для нашего гейта задержка сброса должна быть меньше секунды, а при unmount буфер должен уйти целиком.

Инвалидация кэша. TTL прост, но настройки по умолчанию у NFS (3-60 с) и rclone (5 мин) не проходят гейт видимости правки за 1 с. Callback сообщает об изменении сам и не тратит круги на проверки. Так работают AFS, делегации NFSv4 и watcher в Mutagen.

Кэш отсутствующих имен (negative dentry). Инструменты часто проверяют файлы, которых нет, например конфиги в родительских каталогах. NFS с `lookupcache=pos` перепроверяет такие записи, FUSE по умолчанию их вообще не кэширует. Такой кэш экономит круг на каждой проверке, но должен сбрасываться, когда пользователь создает файл.

## Baseline

Стартовый кандидат это протокол «один запрос на операцию» без кэша. Каждый вызов `stat`, `readdir`, `open`, `read` и `write` уходит отдельным запросом на сторону пользователя и ждет ответа. Кэша, предвыборки, пачек и сжатия нет. По духу это SSHFS с выключенным кэшем (`-o cache=no` в 2.x, `dir_cache=no` в 3.x) и без `kernel_cache`.

Почему он.

1. Он корректен по построению. Каждое чтение идет к источнику правды, каждая запись сразу ложится на диск пользователя. Гейты видимости и сохранности записей выполняются без ухищрений. Проверку пути и режима только для чтения делает сервер.
2. Его время легко предсказать. Оно примерно равно N × RTT + V / B. Здесь N это число файловых операций в трассе, RTT это время круга до пользователя, V это объем переданных данных, B это полоса.
3. Каждая оптимизация на арене видна как отдельный выигрыш и отдельный риск нарушить гейт.
4. Он близок к тому, что люди ставят на практике через sshfs. Результаты проще сравнить с привычным опытом.

## Что из этого может найти арена

Эволюция меняет код протокола, поэтому может заново открыть и скрестить почти все идеи из таблицы.

- TTL-кэш атрибутов и имен как в NFS и FUSE, но с TTL меньше T или с проверкой по событию.
- Push-инвалидацию в духе callback AFS и делегаций NFSv4. Сервер у пользователя следит за папкой и сам шлет уведомления. При T = 1 с это единственный способ держать длинный кэш и пройти гейт.
- Предвыборку дерева и метаданных при монтировании, как начальная синхронизация Mutagen, и выдачу имен вместе с атрибутами как READDIRPLUS.
- Пачки запросов как COMPOUND в NFSv4 и обход нескольких компонентов пути одним RPC как в LISAFS.
- Ленивую загрузку кусками и чтение с опережением как в rclone и FUSE, с отдельной эвристикой для начала и конца файла.
- Выдачу маленьких файлов целиком одним ответом как в AFS.
- Write-back с ограничением задержки сброса меньше T и полным сбросом при unmount.
- Сжатие и чанки по содержимому как в LBFS. Это выигрывает на полосе 50 Мбит/с для больших файлов и повторных записей.
- Кэш отсутствующих имен со сбросом по событиям от сервера.
- Использование паузы 2-8 с между вызовами агента для фоновой предвыборки и сброса записей.
- Предсказание следующих обращений агента по истории сессии. Это автоматический аналог hoarding из Coda и опциональная ML-часть проекта.

Несколько вещей симулятор не проверит.

- DAX и общую память virtiofs. Они работают только с локальной ВМ.
- Поведение page cache ядра и лимиты размера FUSE-запроса. В симуляторе их нет или они упрощены, их проверим на Linux с tc netem.
- Поведение TCP при потере 1%, то есть окно перегрузки и блокировку очереди. Результат зависит от модели сети в симуляторе.
- Работу без связи из Coda. В метрике нет обрывов, есть только потери пакетов.
- Перенос поиска на сторону пользователя как в VS Code Remote. Это меняет интерфейс агента. Арена может прийти только к его следу внутри ФС, к предвыборке целого поддерева пачкой.
