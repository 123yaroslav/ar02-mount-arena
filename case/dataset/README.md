# Данные

## Источник

Данные синтетические, их делает генератор [generate.py](generate.py) поверх `mountsim/tree.py` и `mountsim/scenario.py`. Распределения деревьев сняты с 64 открытых репозиториев GitHub, по 8 на Python, TypeScript, JavaScript, Go, Rust, Java, C++ и Ruby. Сбор делает [scripts/collect_repo_stats.py](../../scripts/collect_repo_stats.py) через git trees API без клонирования. Итог лежит в `mountsim/data/repo_stats.json` (число файлов на репозиторий, распределение глубины, размеры текстовых и бинарных файлов, доля текста, расширения, самый крупный файл).

Генератор строит дерево так. Число файлов берется из распределения реальных репозиториев. Глубина каждого файла берется из распределения глубин. Каталог выбирается процессом китайского ресторана, где новый каталог появляется с весом 8, а существующий выбирается пропорционально числу файлов в нем. Размер файла берется из квантилей реальных размеров отдельно для текста и бинарников. В каждое дерево добавляется один большой файл от 4 до 24 МБ (лог или бинарник) и одна-две ссылки, ведущие за пределы папки. Текст собирается из строк, похожих на код. Его сжимаемость сверена с 8 настоящими репозиториями ([ADR-0008](../../docs/adr/0008-text-realism.md)), zlib сжимает его в 5-6 раз, словарь строк в 1,3-1,6 раза. Бинарники несжимаемые.

Сверка генератора с реальными репозиториями по 60 сгенерированным деревьям.

| Показатель | Реальные | Сгенерированные |
|---|---|---|
| Медианная глубина файла | 3 | 3 |
| Медианный размер текстового файла | 2831 байт | 2840 байт |
| Каталогов на файл, медиана | 0,18 | 0,15 |
| Файлов в непустом каталоге, медиана и 90-й процентиль | 3 и 14 | 4 и 20 |
| Файлов в дереве, медиана | 1650 | 1150, потолок 2000 |

Потолок в 2000 файлов срезает 45% реальных репозиториев. Без него прогон кандидата на крупных деревьях шел бы в разы дольше. Это ограничение кейса, крупные монорепозитории в него не входят.

## Одно распределение

Train, public и private делает один и тот же код с одними параметрами. Отличается только сид split. Каждое дерево полностью попадает в один split.

## Семейства

Семейство это дерево файлов. Из одного дерева получаются 48 экземпляров, это 6 сценариев на 8 профилей сети. У них общая структура каталогов и одинаковые пути, поэтому дерево целиком лежит в одном split. Иначе знание путей из train помогло бы на private. Содержимое файлов у каждого экземпляра свое (отдельный сид содержимого), поэтому кэш между экземплярами отдает неверные байты и ловится гейтом.

## Размеры и обоснование

| Split | Деревьев | Экземпляров | Почему столько |
|---|---|---|---|
| train | 8 | 384 | Хватает, чтобы видеть разброс по деревьям и сценариям. Полный прогон около 50 с при 9 параллельных прогонах на 10 ядрах |
| public | 4 | 192 | Погрешность среднего около 5% при цене прогона около 30 с |
| private | 6 | 288 | Погрешность около 4,5%, финальная оценка один раз |

Откуда погрешность. Сетевого шума нет, джиттер задан сидом экземпляра. Повторный прогон baseline на train дает итог от 0,99 до 1,00, разброс на экземпляр около 0,015 в логарифме ускорения. Он идет от процессорного времени. Основной разброс дают деревья. Классический протокол на восьми деревьях train ускоряется от 1,39 до 1,89 раза, стандартное отклонение по деревьям 0,15 в логарифме. Для среднего по n деревьям это 0,15, деленное на корень из n. При 4 деревьях выходит 0,075 (около 5% по ускорению), при 6 деревьях 0,06 (около 4,5%). Различия кандидатов меньше 5% на public я считаю неразличимыми.

## Формат

UTF-8 JSONL, одна запись на строку, как в `cases/template` арены.

```json
{"id": "train-t00-grep-rtt80-loss1", "input": "{\"format\": \"ar02-v2\", \"tree\": {...}, \"scenario\": {...}, \"profile\": {...}, \"mode\": \"ro\", \"staleness_seconds\": 1.0}", "reference": "{\"baseline_total\": 448.1, \"ops\": 3681, \"final_digest\": \"c2dc2cbe...\", \"format\": \"ar02-v2\"}"}
```

`reference` решателю не передается. В нем время baseline на этом экземпляре, число операций и хеш итогового состояния папки. Метрика по ним отличает честный отчет от отчета с пропущенными операциями или от чужого дерева.

Train лежит в репозитории ([train.jsonl](train.jsonl)), его сид 1. Версии, размеры и хеши всех split записаны в [manifest.json](manifest.json), тест `tests/test_dataset.py` сверяет его с train и генератором. Сиды public и private хранит оператор в `~/.ar02/seeds.json` вне репозитория, сами файлы тоже лежат вне репозитория. Генератор открыт, поэтому знание сида равно знанию данных.

```bash
uv run python case/dataset/generate.py --split train --seed 1 --trees 8 --reference --out case/dataset/train.jsonl
uv run python case/dataset/generate.py --split public --seed-file ~/.ar02/seeds.json --trees 4 --reference --out ~/.ar02/data/public.jsonl
uv run python case/dataset/generate.py --split private --seed-file ~/.ar02/seeds.json --trees 6 --reference --out ~/.ar02/data/private.jsonl
```

Private сгенерирован 06.11.2026 до основной кампании и ни разу не оценивался. Хеши файлов public и private записаны в manifest, так что подменить их после поиска незаметно нельзя. Деревья split не пересекаются. Проверочный прогон на Opus шел только по train и public.
