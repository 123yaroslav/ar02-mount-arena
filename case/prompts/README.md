# Уточнения кейса для исследователей

Ты ищешь протокол монтирования папки пользователя в песочницу агента. Кандидат это каталог `case/ways/<id>/`, скопированный с родителя. Менять можно только `protocol/client.py`, `protocol/server.py` и `NOTES.md`. `solve.py` остается байт в байт как у baseline. Проверка `uv run python scripts/check_candidate.py case/ways/<id>`.

Интерфейс протокола описан в docstring файлов baseline и в [README кейса](../README.md). Симулятор `mountsim/` читать можно и нужно, менять нельзя. Особенно полезны `netmodel.py` (как считается время доставки), `oracle.py` (что считается нарушением) и `scenario.py` (что делает агент).

Замер на train.

```bash
uv run python scripts/evaluate.py --candidate case/ways/<id> --data case/dataset/train.jsonl --out results/v2/<id>/train.jsonl
```

Train открыт полностью, можно делать свои подвыборки (`--limit`, свой JSONL) и смотреть отчеты по экземплярам. Public возвращает только общий score через оценщик. Private не возвращает ничего.

Что зафиксировано. Симулятор, модель сети, сценарии, T = 1 с, метрика, данные и split, лимит предложенных решений.

Что держать в голове.
- Одно нарушение на любом экземпляре обнуляет весь score. Сначала корректность, потом скорость.
- Уведомления сервера идут по тому же каналу, что и данные. Если канал занят большой передачей, уведомление опоздает, и чтение из кэша станет устаревшим.
- Подтвержденная запись должна дойти до пользователя за 1 с даже при RTT 200 мс и потерях 1%.
- Процессорное время клиента и сервера входит в итог. Сжатие и сложные эвристики не бесплатны.
- Пауза LLM между командами 2-8 с. Работа в паузе не входит в ожидание агента, но занимает канал.
- В `NOTES.md` запиши гипотезу, родителя, изменение, score на train с разбивкой по сценариям и профилям и вывод, в том числе отрицательный.
